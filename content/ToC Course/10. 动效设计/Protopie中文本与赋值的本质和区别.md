先一句话结论： 
**赋值 = 修改「变量容器内的数据」（可以持续运算、存储结果）； 
文本反应 = 修改「画布上文本图层的显示内容」（只负责渲染展示，不能持久保存计算结果）。** 

你观察到的现象：
**赋值能写 `num = num + 1` 持续加减乘除，文本图层不能直接自增运算，根源就在二者定位完全不同。**

## 一、两者本质定义
### 1. 赋值（Assign）
操作对象：**变量（Variable）** 变量是一块独立的数据存储空间，分为：**数字类型 / 文本类型 / 布尔类型**。 ✅ 本质：**读写内存里的数据仓库**

- 赋值动作：`变量名 = 表达式`
- 执行后：**永久覆盖变量内部存储的值**，新值会保留下来，供下一次逻辑继续使用
- 数字变量天然支持四则运算：`score = score + 1`、`money = money * 1.05`

> 类比：手机备忘录里存着数字，每次打开可以读取、修改、保存。


### 2. 文本反应（Text，修改文本图层内容）

操作对象：**画布上的文本图层（Layer）** ✅ 本质：**界面渲染指令，只控制“屏幕显示什么文字”** 文本图层本身**没有存储能力**，它只是视图，不是存储器。 你可以在文本表达式里读取变量、做临时计算，**但是计算结果不会自动保存到任何地方**。

> 类比：电脑显示器，只能展示画面；显示器本身存不住数字。


## 二、为什么「文本不能做自增运算，赋值可以」
❌ 错误思路：直接给文本图层写 `textLayer.text = textLayer.text + 1`
看上去语法好像可行，但原型逻辑里几乎没人这么用，坑非常大：
1. **文本图层没有状态记忆** 文本图层的值只用来渲染；你每次刷新、触发其他交互，很容易丢失、读取异常。
2. **数据类型陷阱** 图层`.text`永远是**文本字符串**。 比如文本显示“100”，它是字符串 `"100"`； `"100"+1` 在ProtoPie表达式里不会得到101，大概率触发类型错误，或者变成拼接 `"1001"`。


✅ 正确思路（标准写法）
1. 先用【赋值】操作**修改数字变量**：`count = count + 1`（运算+持久保存）
2. 再用【文本】反应，读取变量展示：文本表达式填入 `count`（仅渲染）

**运算发生在变量赋值阶段，文本只负责最终展示。**

## 三、完整对比表

|维度|赋值（Assign 动作）|文本（Text 修改图层动作）|
|---|---|---|
|**操作目标**|项目变量（数据仓库）|画布文本图层（UI视图）|
|**核心职责**|存储、运算、持久保存数据|界面展示文字，纯渲染|
|**能否自增 `x=x+1`**|✅ 数字变量完全支持|❌ 不推荐、极易出错，无持久存储|
|**数据类型**|区分 Number / Text / Boolean|获取到的值一律是文本字符串|
|**生命周期**|变量值一直保留，跨触发有效|只影响即时画面，没有独立存储|
|**使用位置**|交互响应流程中间，负责逻辑计算|交互末尾，输出可视化结果|
|**跨页面访问**|✅ 全局变量全场景可用|❌ 只能访问当前场景图层|

## 四、两个极易混淆的误区澄清
误区1：“文本里面不能写表达式？”
❌ 不对！ 文本图层的内容框**支持表达式**，可以写简单计算：`price * tax`。 ⚠ 区别：**这里只是临时算出一个值用来显示，不会把结果存起来。** 下一次想要继续运算，依然要依靠变量。
示例：
- 文本表达式写 `a + b` → 只是**显示 a+b 的结果**，a、b本身不变
- 赋值写 `c = a + b` → **把计算结果存入c，后续逻辑可以继续拿c运算**


误区2：“我能不能完全不用变量，只用文本图层做计数器？”
技术上勉强能读取图层文本再转数字运算，但属于反规范做法：
- 输入框/图层文本是字符串，必须套 `tonumber()` 转换；
- 图层隐藏、场景切换、组件复用后，经常读取不到值；
- 逻辑难以调试，复杂交互一定会出bug。 
- 👉 ProtoPie官方设计范式：**逻辑运算交给变量赋值，展示交给文本图层。**


## 五、最简实战模板（计数器例子）
1. 创建数字变量 `count = 0`
2. 按钮点击触发两条响应： ① **赋值**：`count = count + 1`（运算+保存） ② **文本**：选中数字文本图层，表达式填入 `count`（展示）


## 六、快速记忆口诀
**变量赋值管数据，负责计算存结果； 文本图层管显示，只做渲染不存数； 所有加减乘除，优先放在赋值里执行。**

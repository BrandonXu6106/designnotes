> **参会人员**：产品经理（主持）、工程师、设计师、测试人员
>**---------------对话节选---------------**
>此处省略产品需求讲解10000字.........
>- 产品经理：“大家对于这次的需求变更有什么问题吗？”
>- 设计师：“没问题，有几个按钮的颜色我得再想想”
>- 测试人员：“当网络异常时产品该如何提示或跳转要补充清楚”
>- 工程师：”........"

>- 工程师：“不是复杂不复杂的问题，是得把数据结构调整一下，然后重新调接口，后端和前端都得改（内心PS：不复杂你上）”
>- 产品经理：”......"


>参与产品设计并通过与工程师协作来共同研发产品的产品经理都需要懂技术



## 1. 产品思维 VS 技术思维
### 1.1. 思维定义
![[Excalidraw/产品与技术思维.excalidraw|产品与技术思维.excalidraw|468]]

**产品思维(人)**：从==用户价值==出发，在满足商业战略和业务目标的同时, 寻求==产品路径==满足用户需求
**技术思维(机器理性)**：从==功能和工程==实现出发，在满足产品需求的同时,  寻求==可复用技术架构==和==低开发成本== 

### 1.2. 思维运用
![[Excalidraw/产品与技术思维的实现.excalidraw|产品与技术思维的实现.excalidraw|537]]

==产品思维先行==，技术思维是确保产品能成力现实的有利前提和必要==工具==
   
## 2. 非技术背景PM的技术学习方法
### 2.1. 技术的了解程度
非技术背景的产品经理对技术的了解程度：“==知其然，不必知其所以然==”
学习技术知识的方式：
1、实际工作中总结
2、与工程师进行==理解层面==的沟通
3、阅读技术规格文档（数据库、接口设计文档）
技术是工具，是实现产品构思的一种方式，不必把技术当成做产品的拦路虎

案例: 基于客户端和服务器的基础技术架构
![[Excalidraw/cs基础技术架构.excalidraw|cs基础技术架构.excalidraw|453]]

编程语言   数据结构   逻辑控制 ( 遍历 穷举 -- ifelse/switch... )   
程序=数据结构+算法
`````
用户登录程序
数据结构:用户名\密码
程序表达(伪代码): 
if(用户名与密码不为空){
	执行登录操作:
}else{
	提示用户错误信息
}
`````

### 2.2. 与工程师的沟通配合
成为**沟通组织者**，而不是命令或者质问方
**沟通组织者**：明确问题，协同参与方聚焦解决方案并达成一致

多用“**我们**”代替“我”
多用“**一起**”、“共同”代替“你"
多用“**你觉得呢**”代替“就是这样”

遇到不懂的技术问题时，多**引导**和**转移**，多请教和理解

1. PM (沟通发起方): 表达核心观点
2. 工程师 (沟通参与方): 反馈理解
3. PM: ==重复并确认对方理解==
4. 工程师: 二次确认理解


> [!success] 
> 懂技术不如懂产品，技术把握理性，==产品把握人性==


## 3. PM在工作中如何预防挖坑和被挖
从技术角度考虑产品设计的几个原则：
1、==功能兼容性==
2、==数据兼容性==
3、==功能及数据流程闭环==
挖坑示例：
1、新增的视频通话功能在**新老版本间**的兼容
通讯类App产品中在文字沟通的基础上新增视频通话功能，新版本上线后向老版本发起视频通话时无法接通（新老版本的更新提示）
2、**时间格式**从12小时制到24小时制的变化
老版本时间格式为 “1:23:21 pm"
新版本时间格式为“13:23:21"
（产品上线更新后需要对历史数据做批量处理）
3、头像更新后如何整体刷新的策略设计
社交产品中，用户A头像更新后，在好友B那如何刷新A的头像的策略设计？
（1）A更新头像后，批量更新其所有好友
（2）B主动查看A的页面时检查并更新

### 3.1. 如何评估技术可行性
从技术角度评估技术可行性的方法：
1、==市场上是否有同类产品功能==
2、==现有团队是否具备关键技术能力==
3、==已有的技术架构是否支持新方案==

### 3.2. 产品上线前, 技术细节的确认
1、正式上线前，新老版本**产品交叉测试**，确保功能兼容性与数据兼容性
（1）新版本与新版本
（2）新版本与老版本
（3）老版本与新版本
2、产品后台配置文件是否已经更新到最新状态
（1）版本号更新，是否通过版本号控制产品升级
（2）数据访问接口是否能实现对新老版本的兼容
3、上线先后顺序的控制策略
（1）要求服务器端先上线
（2） 客户端不同平台的上线时间点（要求同时上线或者可先后上线）
